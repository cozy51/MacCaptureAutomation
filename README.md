# MacCaptureAutomation

許可された資料の画面キャプチャを行う Swift / SwiftUI の macOS アプリです。DRM・コピー保護の解除や回避は行いません。

## 現在の実装：第1・第2段階

- ディスプレイごとのドラッグ選択、半透明の枠、Esc キャンセル
- 範囲の名前付け、複数プリセット、再設定、削除
- UserDefaults に JSON 形式で保存し、再起動後に復元
- ディスプレイ ID / UUID、解像度、スケール、画面配置、絶対・相対座標を保存
- ScreenCaptureKit のテストキャプチャと画像プレビュー
- 画面収録権限の確認、未許可時の停止、システム設定への案内
- ディスプレイ構成変更時の停止と、ユーザーによる範囲再設定
- 日本語 UI と今回の起動中の実行ログ

キャプチャは1ディスプレイ内の範囲に限定します。絶対座標は AppKit の左下原点、相対座標は画面左上原点のポイントです。出力ピクセル数は範囲のポイント数 × backingScaleFactor です。アプリ自身のウィンドウはキャプチャから除外します。macOS 標準スクリーンショットの範囲履歴は使用しません。

## 必要環境・インストール

macOS 14.0 以降、Xcode 15 以降。外部パッケージや API キーは不要です。Xcode の Command Line Tools を選択してください。

1. `MacCaptureAutomation.xcodeproj` を Xcode で開く。
2. `MacCaptureAutomation` ターゲット、実行先 `My Mac` を選ぶ。
3. Signing & Capabilities で自分の Team を指定し、Signing Certificate が Apple Development になっていることを確認する。
4. Run（Command + R）で起動する。

App Sandbox は無効です。後続の他アプリへの自動操作を想定した構成です。配布用の署名・公証は未設定です。

## コマンドラインビルドと .app（権限の実機確認には下記の署名付きインストールを使用）

リポジトリのルートで実行します。

```sh
xcodebuild -project MacCaptureAutomation.xcodeproj \
  -scheme MacCaptureAutomation -configuration Debug \
  -derivedDataPath build build CODE_SIGNING_ALLOWED=NO
open build/Build/Products/Debug/MacCaptureAutomation.app
```

Release のローカル成果物は次の手順で生成します。

```sh
xcodebuild -project MacCaptureAutomation.xcodeproj \
  -scheme MacCaptureAutomation -configuration Release \
  -derivedDataPath build build CODE_SIGNING_ALLOWED=NO
```

生成先は `build/Build/Products/Release/MacCaptureAutomation.app`。この未署名アプリは配布用ではありません。一般配布には Developer ID 署名と公証が別途必要です。権限の再許可を避けるため、実行するアプリの場所と署名を安定させてください。

## macOS 権限

環境設定画面で「画面収録の許可を要求」を押し、システム設定 → プライバシーとセキュリティ → 画面収録でアプリを許可します。許可変更後は必要に応じてアプリを終了・再起動してください。画面収録が未許可の場合、キャプチャは開始しません。

アクセシビリティの状態も表示しますが、第1段階では不要です。後続のキー送信や UI 操作を実装する際に必要です。

## 初回動作確認・受け入れ手順

1. 権限未許可で範囲を選び、「テストキャプチャ」が権限エラーで止まることを確認。
2. 画面収録を許可して再起動。許可されたテスト資料を表示する。
3. 「新しい範囲を選択」でドラッグ。枠と保存座標を確認。Esc でのキャンセルも確認。
4. 名前を付けて撮影し、プレビューの範囲・縦横・ログのピクセル数を確認。
5. Retina と外部ディスプレイで、ポイント数 × 表示スケールと出力ピクセル数を比較。
6. 別の範囲を保存し、プリセット切り替え、再設定、削除を確認。
7. アプリを終了・再起動して名前、選択中のプリセット、座標が保持されることを確認。
8. macOS 標準スクリーンショットの範囲を変更しても本アプリの保存範囲が変わらないことを確認。
9. 画面配置・解像度の変更、外部画面の取り外しで撮影が停止し、再設定を促すことを確認。再選択後に撮影を確認。
10. 左・右・上・下に配置した外部画面で、選択位置と撮影結果が一致することを確認。

設定はこのアプリの UserDefaults の `capturePresets.v1` と `selectedPreset` に保存します。画像のファイル保存は未実装です。自動処理の単発テストでは画像をクリップボードにコピーします。

## 次の段階と制約

Google スライド背景設定は第3段階の単独テストを実装しています（自動成功判定と繰り返しへの組み込みは未実装）。繰り返し、操作エディタ、ウィンドウ位置管理、永続的な実行履歴は未実装です。自動処理画面では第2段階の単発テストを実行できます。

背景設定は Mac 上で Accessibility API によるメニュー取得、画像選択状態、操作後の実際の背景化を単独検証してから実装します。メニューが閉じたことだけを成功判定にせず、画像オブジェクトの全面配置で代用しません。対象タブを確実に確認できない場合や結果が不明な場合には停止する方針です。現在は単発のキー操作と撮影・貼り付けテストに対応しています。

## 第2段階：Macでの確認手順

1. システム設定のアクセシビリティでこのアプリを許可し、再起動する。未許可時は自動処理が停止することを確認する。
2. KindleとChromeを手動で起動する。自動処理画面のKindle識別子は通常 `com.amazon.Kindle`。異なる版の場合はその版のBundle Identifierに変更する。
3. 許可されたテスト資料をKindleで表示し、キー送信テストを下矢印で実行する。ページが1回だけ進むことを確認する。修飾キーと仮想キーコードを編集できる。
4. 書き込み可能なテスト用GoogleスライドをChromeの前面タブで開く。スライドの編集キャンバスにフォーカスを置き、URLをアプリに設定する。
5. 保存済み範囲を選び「1回だけ実行：撮影→貼り付け」を押す。Kindle切り替え、撮影、クリップボードコピー、Chrome切り替え、Command+V送信の順を確認する。
6. 貼り付けの成功は自動判定していないため、Chromeで結果を確認する。「貼り付け結果を確認済み」を押すまで再送できない。アプリを終了・再起動してもこの確認待ちは保持される。背景設定、スライド送り、Kindleページ送りはこの転送テストには含まない。
7. Chromeを別のWebサイト、または別のGoogleスライドに切り替え、貼り付け前に停止することを確認する。ChromeがAXDocumentとして現在のURLを公開しない場合も停止する。固定座標やタイトルだけの判定では代用しない。
8. 切り替え待機を10秒にして一時停止、再開、停止を試す。待機は50msずつチェックする。ScreenCaptureKit実行中の中断は結果が返るまで待つが、中断後の貼り付けには進まない。送信済み操作の取り消しは行わない。
9. Kindle/Chromeを終了した場合、権限不足、画面構成変更、クリップボードの変更、前面アプリ変更で停止することを確認する。

設定は `automationSettings.v1`、未確認の貼り付けは `pasteUncertain` に保存する。貼り付け後のエラーや停止でも確認待ちを保持し、無条件の再試行はしない。開始は単発テストに限定している。推定残り時間や完了ページ数は繰り返し実装時に追加予定。

AXのモーダルウィンドウとシートをチェックするが、Webページ内の全ダイアログや編集キャンバスのフォーカスは確実に判定できない。編集可能なテスト用プレゼンテーションで確認すること。貼り付けキー送信を、画像挿入成功や背景設定成功とは扱わない。

第2段階もLinux上ではコンパイル・実機確認ができていません。上記はMacで実施する受け入れ手順です。

### ページ送りキー

Kindleのページ送りの初期値は下矢印（仮想キーコード125、修飾キーなし）です。既存の保存設定も初回更新時に一度だけこの値へ移行します。その後のキー編集は保持します。Chromeのページ送り単独テストも下矢印を送信します。Googleスライドのスライド一覧にフォーカスを置いてから実行し、次のスライドが選択されることを確認してください。画像・テキストの編集状態では下矢印が別の操作になるため、実際のページ送りは手動確認が必要です。自動繰り返しへの組み込みは未実装です。

### アプリ切り替えの確認

macOS 14以降の協調的なアプリ切り替えに合わせ、実行アプリから対象アプリへアクティベーションを譲ります。対象が既に前面の場合は切り替え要求を省略します。切り替え要求の戻り値だけで失敗判定せず、最大5秒の待機で前面アプリのPIDを確認します。確認できない場合や待機後に別アプリへ移動した場合はキー送信を停止します。MacでKindle→撮影→Chromeの転送と、対象ウィンドウを閉じた場合の停止を確認してください。この修正の実機確認は未実施です。

## 許可設定を繰り返さないための運用

初期の署名指定が不足していたため、Teamを設定せずビルドした場合、アドホック署名や未署名のアプリになり、更新でmacOSの権限登録と一致しなくなる可能性がありました。プロジェクトはApple Development署名を明示する構成へ変更しました。TeamはユーザーのMacで指定する必要があります。

### 最初の1回

1. Xcode → Settings → Accounts にApple Accountを追加する。
2. プロジェクト → TARGETS → MacCaptureAutomation → Signing & CapabilitiesでAutomatically manage signingをON、Teamを自分のものに設定する。Bundle Identifierは `com.cozy51.MacCaptureAutomation` のまま使う。
3. Signing CertificateがApple Developmentになっていることを確認する。証明書がない場合はAccounts → Manage CertificatesでApple Development証明書を作成する。アドホック署名（Sign to Run Locally）はこの運用では使用しない。
4. Macのターミナルで署名可能な証明書を確認する。

```sh
security find-identity -v -p codesigning
```

5. リポジトリのルートで表示された証明書名を指定する（例の名前を自分のものに置き換える）。

```sh
bash scripts/install-local.sh "Apple Development: 自分の名前 (識別子)"
```

アプリは `~/Applications/MacCaptureAutomation.app` にインストールされ、起動する。このアプリを画面収録とアクセシビリティへ追加し、許可後にCommand+Qで終了・再起動する。古いビルドの登録が残っている場合は最初の移行時だけ、古いアプリの項目を削除してこのアプリを登録する。毎回のtccutilリセットは行わない。

### 次回以降

アプリを終了して、同じ証明書名で上記スクリプトを実行する。通常の利用はFinderのホーム → Applicationsから起動し、XcodeのDerivedDataにある別のコピーを混在させない。環境設定に実行中のパスとBundle Identifierを表示するので確認できる。

スクリプトは署名を検証し、既存版とのdesignated requirementが異なる場合は更新を停止する。既存版がアドホック署名の場合は、初回移行として既存アプリを別の場所へ保管する必要がある。macOSの権限を勝手に変更したり、検証を無効にしたりはしない。

証明書を利用できない場合はこの署名付き運用を完了できない。エラー文を確認すること。安定した署名・場所でもmacOSの更新やシステム方針によって再承認が必要になる場合があり、永久に不要とは保証できない。

### 確認

初回に両権限を許可してテスト撮影とKindleキー送信を確認する。ソース更新後、同じ証明書で再インストールし、再許可なしで両操作ができるか確認する。この署名・権限保持の検証はMacで行う必要があり、Linux環境では未実施。

### 撮影後のChrome切り替え

Kindleが前面の間は実行アプリ自身がバックグラウンドになるため、実行アプリからのactivationの譲渡だけではChromeへ移れない場合がある。NSWorkspaceのopenApplicationを使い、既存のアプリをアクティブ化する要求へ変更した。新規プロセスを作らない設定とし、要求後にPID・前面状態・対象プレゼンテーションを検証してからキーを送る。タイムアウトでは現在の前面アプリを表示する。最小化を検出したわけではないため、最小化解除を求める文言は削除した。Macで撮影後のChrome切り替え、キャンセル時の停止、対象URL不一致時の停止を確認する必要がある。実機確認は未実施。

## 第3段階：背景設定の単独テスト

日本語メニュー「画像を背景に設定」（英語の場合はSet image as background）をAccessibility APIで検索し、AXPressで実行する。固定座標でのクリックや画像の拡大配置では代用しない。撮影、貼り付け、スライド・Kindleのページ送りはこのテストに含まない。

### 通常テスト

1. 同じ署名・同じ場所のアプリを最新版へ更新する。
2. 編集可能なテスト用GoogleスライドをChromeで開き、画像を1枚貼り付けて選択する。
3. アプリの対象URLを設定し、「背景設定テスト」を押す。
4. Chromeの前面状態・対象URLを検証する。AXで選択画像が確認できた場合のみShift+F10を送ってメニューを開く。
5. 有効な背景設定項目が一意に見つかり、AXPressが利用できる場合のみ実行する。

### 選択画像を取得できない場合

ChromeのCanvas実装ではAXImageや選択状態が公開されないことがある。その場合、通常テストは安全に停止する。「メニューを手動で開いてテスト」を押し、Chromeに切り替わった後5秒以内に選択画像を右クリックする。開いたメニューに一意の有効な背景設定項目があることを操作可能な状態の根拠として、メニュー項目だけを実行する。この方式は選択と右クリックの自動化を実証したものではない。メニュー項目自体がAXに公開されない場合は、この方式も停止する。メニューが開いたままアプリをクリックすると閉じるため、Chromeに切り替わった後は結果が出るまで操作しない。

### 結果の確認と制約

AXPressの成功は要求の受理、メニューが閉じたことはUIの変化であり、背景設定の成功とは区別する。Googleスライドの実際の背景化を現時点のAX情報だけで確実に検証できないため、結果確認待ちで止める。選択枠が消え、画像をクリックしてもオブジェクトとして選択できず、スライド全面の背景になったことを手動確認してから「背景設定の結果を手動確認済み」を押す。失敗した場合も手動で状態を確定・修正してから確認する。実行後のエラーや停止では自動再試行しない。確認待ちは `backgroundUncertain` に保存され、アプリ再起動後も保持する。確認待ちの間は新たな背景操作と撮影→貼り付けを禁止する。

### Macでの受け入れ確認

- 正しいURLのテスト用スライドで通常テストを実施し、選択確認・メニュー検索・実行・手動確認までのログを確認する。
- 選択情報を取得できなければ、手動メニュー方式でAXPressによる背景化を確認する。
- URL不一致、画像未選択、背景設定項目のないメニュー、アクセシビリティ未許可で意図しない操作をしないことを確認する。
- メニューを開く前の停止、実行後の停止、アプリ再起動後の確認待ち保持を確認する。
- 既に背景化した画像に再実行しないことを確認する。

Linux環境ではSwift/macOS SDKがないため、この追加機能のビルド・実機確認は未実施。Chromeがメニューと選択状態をどう公開するかは実機で確認が必要。単独テストの安定性と結果検証方法が確立するまで、自動繰り返しへは組み込まない。

### メニュー項目の公開操作

メニュー項目はAXPressではなくAXPickを公開する場合があるため、公開操作一覧からAXPick、AXPressの順に利用可能な操作を選択する。どちらも存在しない場合は公開操作名をエラーに表示して停止する。一度実行要求を送った後は、失敗しても別の操作で無条件に再試行しない。実際にChromeが公開する操作と背景化結果はMacの単独テストで確認する必要がある。

Chrome実機で背景設定項目の公開操作が `AXShowMenu, AXCancel, AXConfirm` であることが確認されたため、AXConfirmにも対応した。選択操作はAXConfirm、AXPick、AXPressの順に公開済みのものだけを使う。AXShowMenuやAXCancelで背景設定を代用しない。実行後の結果確認待ちと重複実行防止は維持する。この修正での実際の背景化は未確認。

### 実行アクションが公開されないChromeへの対応

実機で背景設定項目の公開操作がAXShowMenu、AXScrollToVisible、AXCancelのみになるケースを確認したため、AXConfirm/AXPick/AXPressが全てない場合には動的なクリックを使用する。該当項目のAXPositionとAXSizeから中心を求め、システム全体のAXヒットテストでその場所が同じ項目または子要素であることを確認してからクリックする。固定座標、画面解像度に依存する位置、AXScrollToVisibleやAXCancelの代用は使用しない。座標の取得やヒットテストに失敗した場合は未実行で停止する。実行操作を一度送った後のエラーに対してクリックで再試行することはしない。テスト中はメニューを動かしたりマウスを操作したりせず待つ。背景化は従来どおり手動確認し、繰り返しには組み込まない。この方式のMac実機動作は未確認。

## 右クリックメニュー表示の自動化テスト

手動右クリック後の項目実行が実機で確認できたため、通常の「背景設定テスト」はAXImageの選択情報を取得できない場合も、メニュー表示ショートカットを送る方式へ変更した。対象URL・前面状態を先に検証し、メニュー表示後の一意で有効な「画像を背景に設定」項目を実行可能状態の根拠とする。画像が選択されたことをAXで確認したと偽らない。項目がなければ背景設定を行わず停止する。

1. テストスライドに画像を貼り付け、選択枠がある状態にする。
2. 「背景設定テスト」を押す。今回は右クリックせず待つ。
3. メニューを取得できない場合、表示キーをShift+F10からCommand+Shift+バックスラッシュ、またはControl+Shift+バックスラッシュへ変更し、画像を選択し直して再テストする。キー配列・Chrome・スライドのショートカットにより利用可能なキーが異なるため、自動的な連続試行はしない。アプリ切り替え時に編集対象のフォーカスが保持されるかも確認する。
4. 背景化したか手動確認し、結果確認済みボタンを押す。メニュー閉鎖だけを成功判定にはしない。

ショートカットは `backgroundMenuShortcut.v1` に保存する。バックスラッシュはANSI仮想キーコード42を使い、キー配列によって異なる場合がある。メニュー表示の自動化自体はまだMac実機で未確認。手動メニュー方式は維持し、繰り返し処理は追加していない。

## 撮影 → 貼り付け → 背景設定の1回実行

### Macでの確認手順

1. 最新版を同じ署名・同じ場所へ更新し、起動する。

7. 貼り付け後に背景設定が失敗した場合、最初からやり直すと重複するため一連実行を再送しない。既存の画像を選択して背景設定単独テストを行うか、画像を削除して結果を手動確認してから新しい1回実行を行う。

## 編集手順のファイル保存・読み込み

## 指定ページ数の連続処理

自動処理の「連続処理（結果を最後にまとめて確認）」で1〜500ページを指定する。既存の毎ページ確認モードも残す。撮影→画像コピー→Chrome貼り付け→背景設定を連続実行し、2ページ目以降はChromeの新規スライド追加→空白レイアウト→Kindle下矢印125を挟む。開始時に表示されたスライドを1ページ目に使い、最終ページの後には追加・ページ送りをしない。連続モードのスライド準備は新規空白固定で、従来の移動・複製の選択設定とは独立。

途中の手動確認は行わず、全操作終了後に結果をまとめて確認する。背景化・新規スライド作成・ページ送りの成功をAXで自動判定できないため、「操作送信済み」件数を表示し、成功ページ数とは表現しない。対象アプリ前面、対象URL、クリップボード、メニュー要素、動的クリックのヒットテスト等の既存検証は維持し、検出できるエラーでは停止する。検出できないページ送り不発などは最後の目視確認が必要。連続実行中はキーボード・マウスを操作しない。

一時停止・再開・停止は共有実行制御を使う。一時停止は操作の区切りと待機中に反映し、すでに送信されたクリック・キーを取り消さない。停止・エラー後の途中再開や自動再試行は行わず、操作結果未確認を保持する。再起動後も未確認フラグと直前の操作段階が残り、実行を無条件に再開しない。全体の結果と両アプリの位置を確認して「処理結果とページ位置を確認済み」を押す。再実行時は現在のKindleページと現在のスライドから新たに指定数を処理する。

### 連続処理の最初の実機確認

1. テスト用のGoogleスライドを開き、開始用スライドを空白レイアウトにする。編集キャンバスを選択し、Kindleには開始ページを表示する。

3. 連続処理のページ数を2にして開始。途中では操作せず、貼り付け・背景設定・新規空白追加・Kindle送り・2枚目の貼り付け・背景設定の順を確認する。
